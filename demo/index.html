How the MARL system works

Problem
Requests arrive at 4 regional load balancers (Mumbai, Singapore, Frankfurt, Virginia) and must be placed on 5 shared VMs with capacities 7, 5, 4, 2 and 2 jobs per tick.
Agents
One independent Q-learner per region. No agent sees the others' choices or Q-tables.
State
Each VM's load bucket (idle, busy, saturated): 35 = 243 states.
Action
Which VM receives the job (5 actions).
Reward
−(queue wait + network delay). A job sent to a down or full VM is dropped and scores −3000 ms.
Policy
ε-greedy. ε decays from 1.0 to 0.02. A VM failure raises ε to 0.3 so agents re-explore.
Q(s,a) ← Q(s,a) + α [ r + γ · maxa′ Q(s′,a′) − Q(s,a) ]   α = 0.1, γ = 0.3

Why it is multi-agent: the best VM for Mumbai depends on what the other three regions send there. From each agent's view the environment keeps changing as the others learn (non-stationarity), yet they settle on a split of the pool without talking to each other.

Demo script for class

  1. Press Reset learning. With ε = 1 the agents act randomly, so MARL latency tracks the Random line.
  2. Set speed to 8× for about 15 seconds. As ε decays the blue line falls below both baselines.
  3. Point at the routing table. Regions favour nearby, high-capacity VMs and keep the small VMs lightly loaded.
  4. Click vm-l to take it down. Baselines keep sending jobs to it and drop them. MARL re-explores and reroutes.
  5. Press Traffic spike to show behaviour under a 1.5× burst, then bring the VM back up.

Baselines are capacity-blind and have no health checks, like plain DNS round-robin. Everything runs in your browser; all three policies see the same random arrivals each tick.
